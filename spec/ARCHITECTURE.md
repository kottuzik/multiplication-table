# ARCHITECTURE — כפל כיף / Times Fun

> מסמך ארכיטקטורה המבוסס על PRD – אפליקציית לימוד לוח הכפל לילדים. עודכן: 20.10.2026.

## 1. החלטה ארכיטקטונית

המוצר יהיה **Static Single-Page Application (SPA)** המותקן כ-**Progressive Web App (PWA)**. כל יצירת התרגילים, בדיקת התשובות, הצגת המשוב והחלפת השפה מתבצעים בדפדפן. לאחר טעינה מוצלחת ראשונה ושמירת קובצי האפליקציה ב-Cache, השימוש אינו דורש רשת.

לא נדרשים Backend, Database, Authentication, שרת API, אחסון קבצים בענן, שירות AI או אינטגרציות חיצוניות. אין להוסיף אותם במסגרת המוצר הנוכחי.

### נימוקי בחירה וחלופות שנבדקו

- **React לעומת Vue ו-Vanilla TypeScript:** שלושתן מתאימות למוצר קטן. React נבחר בשל בשלותו, תיעוד רחב, קהילת מפתחים, דוגמאות קוד וניהול UI צפוי. Vanilla TS עשוי להניב Bundle קטן יותר, אך אינו נדרש כדי לעמוד באילוצים. אין צורך ב-Next.js או SSR.
- **Vite לעומת Create React App ו-Next.js:** Vite מתאים ישירות ל-SPA סטטי; אין צורך בתשתית Server Rendering.
- **CSS רגיל לעומת Tailwind ו-Component Libraries:** כמות מסכים קטנה, ודרישות RTL ונגישות מצדיקות CSS פשוט ללא תלות עיצובית נוספת.
- **vite-plugin-pwa/Workbox לעומת Service Worker ידני:** מפחית טעויות ב-Precache ובניהול גרסאות; יש להגדיר במפורש את הנכסים שנדרשים Offline.
- **GitHub Pages לעומת Vercel ו-Cloudflare Pages:** שלושתן מסוגלות לארח Static Site; GitHub Pages מתאים לברירת המחדל שבבקשה ולפריסה אוטומטית דרך GitHub Actions, ללא Backend.
- **אחסון:** אין צורך ב-Supabase, Firebase או IndexedDB. שמירת מצב התרגול בין סשנים אסורה לפי ה-PRD; רק העדפת השפה נשמרת ב-`localStorage`, בכפוף להנחת ה-PRD.

### עלויות ומגבלות

- עבור Repository ציבורי, GitHub Pages זמין במסגרת GitHub Free. לא צפויות עלויות Hosting לאפליקציה קטנה במסגרת המכסות הרגילות; Domain מותאם אישית, אם ייבחר, עשוי לעלות כסף.
- GitHub Pages הוא Hosting סטטי בלבד; אין בו Backend או Database, וזה תואם לדרישות.
- לפי התיעוד הרשמי: אתר מפורסם עד 1GB, מגבלת תעבורה רכה של 100GB בחודש ו-Deployment timeout של 10 דקות. אם הפרויקט יגדל או ישנה אופי לשירות מסחרי, יש לבחון מחדש את התאמת תנאי השירות.
- Service Worker ו-Cache עלולים להגיש גרסה ישנה עד שהעדכון נקלט; נדרשת אסטרטגיית עדכון בטוחה.
- התקנה ב-iOS תלויה בהתנהגות Safari ובפעולת המשתמש להוספה למסך הבית; אין להבטיח Install Prompt זהה באנדרואיד וב-iPhone.

## 3. מבנה המערכת

```text
GitHub Repository
   └── GitHub Actions → Vite Build → GitHub Pages (HTTPS)
                                      │
                                      ▼
                              Browser / Installed PWA
                              ├── App Shell / Navigation
                              ├── Home Screen
                              ├── Practice Screen
                              │   └── Exercise Engine (local)
                              ├── About Screen / 10×10 Table
                              ├── Localization (he/en)
                              ├── Session State (memory)
                              ├── Language Preference (localStorage)
                              └── Service Worker / Precache
```

### Modules ואחריות

1. **App Shell / Navigation:** מעבר בין `home`, `practice`, `about` באמצעות React State, ללא React Router. הכפתור Back במסכים המשניים חוזר לבית. כפתור "חזרה" של המכשיר/הדפדפן מסונכרן עם הניווט באמצעות History API (ראו ADR-1). כפתור השפה זמין בכל מסך.
2. **Home:** שם המוצר בהתאם לשפה, איור מקומי בנושא מתמטיקה וכפתורי מעבר לתרגול ולאודות.
3. **Practice:** בורר `all` או מספר 1–10, הצגת תרגיל, שדה תשובה, כפתורי בדיקה ודילוג, משוב, מונה תשובות נכונות, כפתור סיום וחלון סיכום (Modal בתוך המסך, לא מסך נוסף).
4. **Exercise Engine:** פונקציות טהורות ליצירת זוג גורמים בטווח 1–10 ולבדיקת תשובה; אין תלות ברשת או בממשק.
5. **About:** טבלת כפל 10×10 המיוצרת מערכים מספריים ומוצגת כטבלת HTML נגישה, וכן הסבר קצר בשפה הפעילה.
6. **Localization:** מילוני מחרוזות מקומיים לשתי השפות; עדכון `lang` ו-`dir` ברכיב המסמך בעת החלפת שפה.
7. **PWA:** Manifest, אייקונים, Service Worker ושמירת App Shell וכל הנכסים הנדרשים לשימוש Offline.

## 4. Data Model וניהול מצב

אין Database ואין שרת. המודל נשמר בדפדפן:

| ישות לוגית | שדות | מיקום ואורך חיים |
|---|---|---|
| `Exercise` | `factorA: number`, `factorB: number` | React State, בסשן בלבד |
| `PracticeState` | `selectedTable: 'all' \| 1..10`, `exercise`, `answerInput: string`, `correctCount: number`, `feedback`, `skipped: Exercise[]`, `reviewQueue: Exercise[]` (התרגילים שנותרו להצגה במעבר "רוצה לפתור"), `isSummaryOpen: boolean` | React State ברמת ה-App Shell (לא בתוך מסך הלימוד), כך שהוא נשמר במעבר בין מסכים; בסשן בלבד. `answerInput`, `feedback` ו-`isSummaryOpen` מתאפסים ביציאה ממסך הלימוד; `skipped` נשמר כמו המונה |
| `Language` | `'he' \| 'en'` | React State; העדפה ידנית ב-`localStorage` בלבד |
| `Translations` | מפת מפתחות למחרוזות בעברית ובאנגלית | קוד Static מקומי |
| `MultiplicationTable` | ערכים מחושבים של 1–10 × 1–10 | מחושב בזמן הצגה; ללא אחסון |

**כלל מחייב:** `correctCount`, רשימת הדילוגים, התרגיל הנוכחי, התשובה והמשוב **לא** יישמרו ב-`localStorage`, `sessionStorage`, IndexedDB או שרת. טעינה מחדש מאפסת את המונה ואת מצב התרגול. סגירת האפליקציה ופתיחתה מחדש מתחילה סשן חדש; אין מנגנון שחזור סשן.

**בחירת שפה:** בתחילת טעינה יש לבדוק העדפה תקינה ב-`localStorage`; אם אין, לבחור אנגלית רק כאשר שפת הדפדפן הראשית היא `en` או מתחילה ב-`en-`, ועברית בכל מקרה אחר (כולל `he` ושפה לא נתמכת). שינוי ידני שומר רק את קוד השפה. אם אחסון הדפדפן חסום, ממשיכים לפעול עם מצב בזיכרון.

## 5. לוגיקת תרגול ו-Data Flow

### יצירת תרגיל

- ברירת המחדל של בורר הטבלאות: `all`.
- ב-`all`: שני הגורמים נבחרים אקראית, כל אחד באופן בלתי תלוי מתוך 1–10.
- בבחירת טבלה `N`: גורם אחד הוא `N`, והאחר נבחר אקראית מתוך 1–10; ניתן להציב את `N` ראשון או שני.
- מותר שהתרגיל החדש יהיה זהה לקודם.
- מעבר לטבלה אחרת יוצר תרגיל חדש מיד, מוחק תשובה ומשוב קודמים ושומר את המונה.

### בדיקת תשובה

1. קלט התשובה מוצג כשדה טקסט עם `inputMode="numeric"`, ולא `type="number"`, כדי לשלוט בתווים ובאורך.
2. השדה מקבל רק ספרות ASCII `0–9`, עד שלושה תווים; תווים אחרים מוסרים גם בהדבקה. התשובה נשמרת כמחרוזת עד לבדיקה.
3. לחיצה על Check/בדיקה עם שדה ריק מציגה הודעת בקשה להזנת תשובה; המונה והתרגיל אינם משתנים.
4. תשובה מספרית השווה ל-`factorA * factorB`: הגדלת המונה בדיוק פעם אחת, הצגת משוב הצלחה ויצירת תרגיל חדש. יש להבטיח שהודעת ההצלחה נראית/מוכרזת גם בעת החלפת התרגיל.
5. תשובה שגויה: הצגת משוב כישלון, השארת אותו תרגיל, ניקוי שדה התשובה, ללא שינוי במונה; ניסיונות חוזרים ללא הגבלה.
5א. אחרי כל בדיקה (כולל שדה ריק) מחזירים את ה-Focus לשדה התשובה, כדי שהמקלדת בנייד תישאר פתוחה. המשוב נמחק עם ההקלדה הבאה בשדה או בהחלפת טבלה.
5ב. דילוג: הוספת התרגיל הנוכחי ל-`skipped` אם אינו קיים בה כבר (השוואה לפי `factorA` ו-`factorB` בסדרם), יצירת תרגיל חדש מהטבלה הנבחרת, ניקוי קלט ומשוב, ללא שינוי במונה. Focus חוזר לשדה התשובה.
5ג. תשובה נכונה לתרגיל שנמצא ב-`skipped` (אותם גורמים באותו סדר) מסירה אותו מהרשימה.
5ד. סיום תרגול: פתיחת חלון הסיכום (`role="dialog"` עם `aria-modal`, Focus עובר לכפתור הראשון בחלון ונשאר בתוכו). החלון מציג את התרגילים בלבד, ללא תשובות. Escape סוגר את החלון בלי לשנות מצב, וה-Focus חוזר לכפתור הסיום.
5ה. **רוצה לפתור:** `exercise = skipped[0]`, `reviewQueue = skipped.slice(1)`, החלון נסגר וה-Focus עובר לשדה התשובה. אחרי תשובה נכונה או דילוג, התרגיל הבא נלקח מ-`reviewQueue` כל עוד היא לא ריקה; אחר כך חוזרים לתרגילים אקראיים. החלפת טבלה מרוקנת את `reviewQueue`.
5ו. **סיים:** איפוס מצב התרגול להתחלה (מונה 0, רשימות ריקות, `all`, תרגיל חדש) וחזרה לבית דרך `history.back()`, כמו כפתור **חזרה**.
6. יש למנוע הפעלה כפולה של בדיקה עבור אותה תשובה נכונה עקב לחיצות מהירות או אירועים חוזרים.
7. שינוי שפה במהלך תרגיל משנה רק מחרוזות ו-RTL/LTR; אינו משנה את הגורמים, התשובה המוקלדת או המונה.

**זרימה מרכזית:** `User Input → Input Validation → Exercise Check → Practice State Update → Immediate UI Feedback`. אין קריאות API.

## 6. ממשק, שפות ונגישות

- שלושה מסכים בלבד: בית, לימוד, אודות. שמות המוצר: **כפל כיף** ו-**Times Fun**.
- כל טקסטי הממשק, כולל הודעות שגיאה, כפתורים, תוויות, שם המוצר והסבר אודות, יהיו בעברית או באנגלית בהתאם לשפה הפעילה. יש להשתמש במחרוזות שבטבלת "טקסטי ממשק (מאושרים)" ב-PRD, ללא תוספות או שינויים.
- `document.documentElement.lang` יהיה `he` או `en`, ו-`dir` יהיה `rtl` או `ltr`. שימוש ב-CSS Logical Properties כגון `margin-inline` ו-`padding-inline`.
- מספרי התרגיל והסימן `×` יישארו בסדר קריא ועקבי גם בממשק RTL, באמצעות בידוד כיווניות מתאים (`dir="ltr"` לרצף המתמטי). גם טבלת 10×10 במסך אודות מקבלת `dir="ltr"` ומוצגת משמאל לימין בשתי השפות.
- חצים בכפתורי ניווט מתהפכים לפי הכיוון (`rtl`/`ltr`), לפי `DESIGN.md`.
- Mobile-first, אזורי מגע גדולים, התאמה למסכים צרים ולשינוי אוריינטציה, ללא גלילה אופקית.
- רכיבי HTML סמנטיים, `label` לשדה התשובה, מצבי Focus ברורים, ניגודיות מספקת ומשוב טקסטואלי שאינו נשען על צבע בלבד.
- משוב על תשובה יוכרז לקוראי מסך באמצעות אזור `aria-live` מתאים, בלי לייצר הכרזות מיותרות.
- טבלת 10×10 במסך אודות תהיה HTML Table עם כותרות שורה ועמודה, ולא תמונה.
- אין להשתמש בפונטים, תמונות או סקריפטים מ-CDN חיצוני בזמן הריצה, כדי לשמר Offline מלא.

## 7. PWA ו-Offline

- להגדיר `Web App Manifest` עם `name`/`short_name`, `start_url`, `scope`, `display: standalone`, אייקונים מתאימים וערכי Theme. שם המוצר במניפסט קבוע: `name` ו-`short_name` = **כפל כיף**, עם `lang: "he"` ו-`dir: "rtl"`; שפת ממשק בתוך האפליקציה תמשיך להשתנות דינמית. אין להבטיח שינוי שם האייקון המותקן בזמן אמת.
- iOS: קובץ `apple-touch-icon` (180×180, ללא שקיפות) הנגזר מאיור הבית, ותגיות `apple-mobile-web-app-title` = **כפל כיף** ו-`apple-mobile-web-app-capable`. ללא תמונות `apple-touch-startup-image`; צבע רקע הדף ו-`background_color` במניפסט זהים, כך שההבזק בפתיחה באייפון יהיה בצבע האפליקציה.
- להשתמש ב-`vite-plugin-pwa` במצב `generateSW` ולבצע Precache של `index.html`, קובצי JS/CSS, איורים, אייקונים ושאר נכסי Static החיוניים. יש לוודא שה-Manifest וקובצי האייקונים זמינים גם Offline.
- להשתמש בנתיבים יחסיים לבסיס הפריסה של Vite, כולל `start_url` ו-`scope`, כדי לתמוך ב-GitHub Pages תחת נתיב Repository.
- אחרי טעינה ראשונה מוצלחת והשלמת התקנת ה-Service Worker וה-Precache, פתיחה מחדש וניווט בין המסכים יפעלו ללא אינטרנט. אין להבטיח Offline אם ההתקנה/ה-Caching טרם הושלמו, או אם המשתמש מחק נתוני אתר.
- עדכונים: גרסה חדשה נכנסת לתוקף רק בפתיחה הבאה של האפליקציה מאפס, ללא הודעה קופצת וללא רענון כפוי באמצע סשן (ראו ADR-3).
- טעינה ראשונה ללא חיבור לרשת אינה נתמכת; במקרה כזה מוצגת שגיאת הדפדפן הרגילה.
- לבדוק התקנה ו-Offline ב-Chrome Android וב-Safari iOS, וכן שימוש בסיסי בדסקטופ.

## 8. APIs, Authentication, Security ופרטיות

- **APIs:** אין API פנימי או חיצוני. כל פעולות המוצר מקומיות.
- **Authentication / Authorization:** לא נדרשים; אין חשבונות או הרשאות משתמש.
- **פרטיות:** אין איסוף פרטים אישיים, Analytics, Cookies למעקב, פרסומות או העברת נתוני תרגול לשרת. העדפת שפה בלבד נשמרת מקומית. Hosting עשוי לייצר רישומי גישה תשתיתיים שאינם בשליטת קוד האפליקציה; אין לטעון שאין כלל רישומי שרת.
- **אבטחה:** פריסה ב-HTTPS, ללא Secrets בקוד לקוח; הימנעות מהזרקת HTML לא מהימן; תלות בספריות מוכרות ועדכון Dependencies; כל הנכסים המקומיים ברישיון מתאים ובטוחים לילדים.
- **תוכן:** אין הצגת התשובה הנכונה או רמזים בשום שלב (גם לא בחלון הסיכום), ואין הוספת משחקים, פרסים, טיימר או סטטיסטיקות מעבר למונה הסשן.

## 9. GitHub, Hosting ו-Deployment

### Repository

- Repository יחיד ב-GitHub המכיל קוד React/TypeScript, נכסים, קובצי PWA, בדיקות, `package.json`, `package-lock.json`, תצורת Vite ו-GitHub Actions.
- `main` מייצג קוד מוכן לפרסום; שינויים יוכלו להיבדק ב-Branches וב-Pull Requests לפני מיזוג.
- לא לשמור Credentials או קובצי `.env` רגישים ב-Repository. אין צורך ב-Environment Variables או Secrets של שירותי אפליקציה במוצר הנוכחי.

### Build ופריסה

1. GitHub Actions מופעל אוטומטית עם Push ל-`main`.
2. סביבת CI מתקינה גרסת Node LTS התואמת ל-Vite ול-vite-plugin-pwa, מריצה `npm ci`, בדיקות ו-`npm run build`.
3. Vite יוצר את תיקיית `dist` עם קובצי האפליקציה וה-PWA.
4. Workflow מעלה את `dist` כ-Pages Artifact ומפרסם באמצעות פעולות GitHub Pages הרשמיות.
5. GitHub Pages מגיש את האפליקציה ב-HTTPS. אין צורך בשרת יישום, במסד נתונים או ב-Database Migrations.

**הגדרת נתיב:** אם כתובת הפרויקט היא `https://<user>.github.io/<repo>/`, להגדיר ב-Vite `base: '/<repo>/'`; אם מדובר באתר Root או Domain מותאם, `base: '/'`. נתיבי האייקונים וה-PWA חייבים להתאים ל-`base`.

**Development:** ניתן לפתח ולבדוק מקומית עם Vite ללא Docker וללא שירות ענן מחייב. ניתן לבדוק גם דרך Preview של Build, אך `vite preview` אינו שרת Production. אין סביבת Supabase, ולכן אין צורך בשני פרויקטי Database או בפרטי גישה ל-Production.

## החלטות מרכזיות (ADRs)

### ADR-1: סנכרון כפתור "חזרה" של המכשיר עם הניווט, ללא React Router
**הקשר:** הניווט בין שלושת המסכים מבוסס על React State, ללא שינוי בהיסטוריית הדפדפן. במצב כזה, לחיצה על כפתור "חזרה" של המכשיר (בעיקר באנדרואיד ובאפליקציה מותקנת) במסך לימוד או אודות יוצאת מהאפליקציה כולה, ומצב התרגול והמונה אובדים. ה-PRD דורש שכפתור זה יחזיר למסך הבית.
**החלטה:** בכניסה למסך משני מוסיפים רשומה להיסטוריית הדפדפן (`history.pushState`), ומאזינים לאירוע `popstate` כדי לחזור למסך הבית. כפתור **חזרה** שבאפליקציה מפעיל `history.back()`, כך ששני הכפתורים מתנהגים זהה וההיסטוריה נשארת עקבית. כתובת העמוד אינה משתנה, ואין שימוש ב-React Router.
**השלכות:** פתרון קטן ללא תלות חדשה. במסך הבית כפתור "חזרה" של המכשיר מתנהג כרגיל. רענון העמוד תמיד פותח את מסך הבית (בהתאם לאיפוס הסשן). אין קישורים ישירים למסכים פנימיים, וזה תואם את דרישות המוצר.

### ADR-2: פריסה ל-GitHub Pages כבר מ-Milestone 1
**הקשר:** התקנת PWA ופעולה Offline בטלפון אמיתי דורשות כתובת HTTPS; שרת הפיתוח המקומי אינו נגיש כ-HTTPS מהטלפון. אם הפריסה מתבצעת רק ב-Milestone האחרון, אי אפשר לבדוק את Milestone 4 (PWA) על מכשירים, ולא ניתן לבדוק את Milestones 1–3 בטלפון.
**החלטה:** Workflow של GitHub Actions (בדיקות, Build ופרסום ל-GitHub Pages) מוקם כבר ב-Milestone 1. מאותו שלב כל Push ל-`main` מפרסם גרסה חדשה. Repository: `kottuzik/multiplication-table`, ולכן `base: '/multiplication-table/'` והכתובת הצפויה `https://kottuzik.github.io/multiplication-table/`. ה-Push עצמו מתבצע רק לאחר אישור המשתמש, לפי הכללים ב-CLAUDE.md.
**השלכות:** כל Milestone ניתן לבדיקה בטלפון בכתובת ציבורית. הפעלת GitHub Pages בהגדרות ה-Repository (Source: GitHub Actions) מתבצעת על ידי המשתמש, בהדרכה. גרסאות ביניים לא גמורות יהיו גלויות בכתובת הציבורית. ה-Repository צריך להיות ציבורי כדי להשתמש ב-GitHub Pages בחינם (אומת על ידי המשתמש: ה-Repository ציבורי).

### ADR-3: עדכון גרסה בפתיחה הבאה בלבד, ללא הודעה
**הקשר:** כשמתפרסמת גרסה חדשה, ה-Service Worker יכול להחליף אותה מיד (ולרענן את המסך באמצע תרגול, כך שהמונה יאבד) או להמתין. הודעה קופצת "יש גרסה חדשה" מבלבלת ילדים.
**החלטה:** `vite-plugin-pwa` מוגדר כך שהגרסה החדשה מורדת ברקע אך אינה מופעלת בכפייה (ללא `skipWaiting` אוטומטי וללא רענון), וללא ממשק הודעה. הגרסה החדשה נכנסת לתוקף כשהאפליקציה נסגרת לגמרי ונפתחת מחדש.
**השלכות:** אין אובדן מצב תרגול באמצע שימוש. מגבלה ידועה: באייפון, אפליקציה מותקנת לא תמיד נסגרת לגמרי, ולכן עדכון עשוי להופיע רק אחרי כמה פתיחות או אחרי סגירה ידנית ממחליף האפליקציות.

### ADR-4: מצב התרגול ב-Reducer ב-App, וחלון סיכום מותאם במקום `<dialog>` מובנה
**הקשר:** מצב התרגול צריך לשרוד מעבר בין מסכים, להתעדכן באופן אטומי (הגדלת המונה והחלפת התרגיל יחד, כדי למנוע ספירה כפולה בלחיצות מהירות) ולהיות ניתן לבדיקה. בנוסף, ב-Chrome לאנדרואיד כפתור "חזרה" של המכשיר סוגר `<dialog>` מובנה במקום לחזור למסך הבית — בניגוד למקרה הקצה ב-PRD ("יציאה ממסך הלימוד כשחלון הסיכום פתוח").
**החלטה:** `useReducer` ב-`App` עם Reducer טהור (`src/practice/practiceState.ts`) ומנוע תרגילים טהור (`src/practice/exercise.ts`), שמקבלים פונקציית אקראיות להזרקה בבדיקות. חלון הסיכום ממומש כ-`div` עם `role="dialog"` ו-`aria-modal`, עם ניהול Focus, לכידת Tab ו-Escape ידניים, והתוכן שמאחוריו מסומן `inert`. ביציאה ממסך הלימוד ה-App מנקה קלט, משוב וחלון פתוח.
**השלכות:** כפתור "חזרה" של המכשיר מחזיר לבית גם כשהחלון פתוח (דרך ה-popstate הקיים, ADR-1). מעט יותר קוד לניהול Focus. לחיצה חוזרת על **בדיקה** מיד אחרי תשובה נכונה (שדה ריק) אינה מחליפה את הודעת ההצלחה. מעבר "רוצה לפתור" ממומש כתור (`reviewQueue`) בתוך אותו Reducer, ו"סיים" כפעולת `reset` שמחזירה את המצב ההתחלתי.

### ADR-5: שפת הממשק ב-React Context, מוחלת על `<html>`, וכפתור השפה זמין גם מעל חלון הסיכום
**הקשר:** כל הרכיבים צריכים את השפה הפעילה; החלפתה חייבת לשנות מיד את `lang` ו-`dir` של המסמך בלי לגעת במצב התרגול. ה-PRD דורש אפשרות להחליף שפה כשחלון הסיכום פתוח, אבל התוכן שמאחורי החלון מסומן `inert` ומכוסה ברקע כהה (ADR-4).
**החלטה:** `LanguageProvider` (`src/i18n/LanguageContext.tsx`) מחזיק את השפה ב-`useState` נפרד ממצב התרגול, ו-`useStrings()` קורא ממנו. `useLayoutEffect` מעדכן `lang`, `dir` ו-`document.title` לפני הציור, כדי למנוע הבהוב RTL באנגלית. השפה ההתחלתית: ערך תקין שמור ← שפת הדפדפן הראשית (`en`/`en-*` = אנגלית) ← עברית. רק המפתח `times-fun:language` נשמר ב-`localStorage`, רק בבחירה ידנית, ובתוך `try/catch`. בחלון הסיכום מוצג עותק של כפתור השפה בשכבת החלון, באותו מיקום כמו בשורה העליונה, בתוך אזור ה-`dialog` (כולל לכידת ה-Tab) — לפי החלטת המשתמש בתכנון.
**השלכות:** אין תלות חדשה; המסכים ממשיכים להשתמש ב-`useStrings()`; היפוך הפריסה והחצים נשען על CSS Logical Properties ו-`[dir]`. עד שה-JS נטען, `index.html` מוגדר עברית (רגע קצר ללא תוכן). כש-`localStorage` חסום, השפה נשמרת בזיכרון בלבד עד לטעינה הבאה.

### ADR-6: אייקונים מוכנים מראש ממקור SVG ריבועי, ו-`registerType: 'prompt'` ללא ממשק
**הקשר:** אייקוני PWA צריכים להיות ריבועיים, ואייקון האייפון חייב להיות אטום; איור הבית מלבני ושקוף. ADR-3 דורש שגרסה חדשה לא תופעל באמצע שימוש וללא הודעה.
**החלטה:** `public/app-icon.svg` הוא אייקון ריבועי עם רקע אטום שנגזר מאיור הבית (הלוח עם `3 × 4 = ?` וכוכב מחייך). קובצי ה-PNG/ICO נוצרים ממנו פעם אחת ב-`npm run generate-icons` (`@vite-pwa/assets-generator`, הגדרות ב-`pwa-assets.config.ts`; אייקון Maskable ואייקון אייפון ללא שוליים לבנים) ונשמרים ב-Repository, כך שה-Build וה-CI אינם מייצרים אותם מחדש. הגדרות ה-PWA נמצאות ב-`pwa.config.ts`: `registerType: 'prompt'` בלי לייבא את מודול ההודעה (הפלאגין מזריק סקריפט רישום פשוט), ללא `skipWaiting`/`clientsClaim`, ו-Precache של `html/js/css/svg/png/ico/woff2` בלבד (ללא קובצי `woff` הכפולים).
**השלכות:** שינוי באייקון דורש הרצה חוזרת של `npm run generate-icons`. אין קוד ממשק לעדכונים; גרסה חדשה ממתינה ונכנסת לתוקף אחרי שכל חלונות האפליקציה נסגרים ונפתחים מחדש (נבדק בדפדפן). Service Worker אינו פועל ב-`npm run dev`; בדיקת PWA נעשית על Build דרך `npm run preview`. מגבלת האייפון מ-ADR-3 נשארת בתוקף.

### ADR-7: כפתור התקנה מבוסס `beforeinstallprompt`, ללא כפתור באייפון
**הקשר:** אחרי הבדיקה בטלפון, המשתמש ביקש כפתור התקנה בתוך האפליקציה, כי ההתקנה מתפריט הדפדפן אינה נוחה. Chrome/Edge (אנדרואיד ומחשב) מאפשרים לאתר להציג את חלון ההתקנה דרך האירוע `beforeinstallprompt`; Safari באייפון אינו תומך בזה.
**החלטה:** `src/pwa/installPrompt.ts` מאזין לאירוע כבר בעליית האפליקציה (לפני ש-React מרונדר, כי האירוע יכול להגיע מוקדם), מונע את הפס האוטומטי של הדפדפן ושומר את האירוע במאגר קטן שנקרא דרך `useSyncExternalStore`. `InstallButton` בשורה העליונה של כל המסכים מוצג רק כשיש אירוע שמור; לחיצה קוראת ל-`prompt()` ומסתירה את הכפתור (אפשר להשתמש באירוע פעם אחת). האירוע `appinstalled` מסתיר אותו גם כשההתקנה נעשתה מתפריט הדפדפן. באייפון לא מוצג כפתור (החלטת המשתמש).
**השלכות:** אין תלות חדשה ואין מצב נשמר. הכפתור לא מופיע כשהאפליקציה כבר מותקנת או פתוחה כאפליקציה מותקנת, וגם לא בדפדפנים שלא תומכים באירוע (Safari, Firefox). Chrome עשוי לא להציע התקנה מיד בביקור הראשון, ולכן לפעמים הכפתור יופיע רק אחרי כמה שניות או בביקור הבא.
